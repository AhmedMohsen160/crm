# نظام إدارة العملاء (CRM) — لمكتب الترجمة

نظام مبيعات متكامل على غرار Zoho، مبني خصيصًا لمكتب ترجمة: تسجيل العملاء،
متابعتهم مرحلة بمرحلة، توزيع المهام على الفريق، وإصدار عروض الأسعار.

الواجهة عربية بالكامل من اليمين إلى اليسار.

---

## ما الذي يفعله النظام؟

| القسم | الوظيفة |
|---|---|
| **لوحة التحكم** | ملخص فوري: قيمة الصفقات المفتوحة، مبيعات الشهر، المهام المتأخرة، وترتيب الفريق. |
| **العملاء المحتملون** | كل من تواصل معك ولم يصبح عميلًا بعد. بضغطة واحدة يتحوّل إلى شركة + جهة اتصال + صفقة. |
| **الشركات** | العملاء المؤسسيون: بياناتهم، الرقم الضريبي، شروط الدفع. |
| **جهات الاتصال** | الأشخاص داخل كل شركة ووسائل التواصل معهم. |
| **الصفقات** | مسار المبيعات (Pipeline) بلوحة سحب وإفلات: جديدة ← عرض سعر ← تفاوض ← فوز/خسارة. |
| **عروض الأسعار** | تسعير حسب الكلمة أو الصفحة أو الساعة، مع حساب الخصم والضريبة تلقائيًا، وصفحة جاهزة للطباعة أو الحفظ PDF. |
| **المهام** | ما يجب عمله، ومن ينفّذه، ومتى — مع تنبيه للمهام المتأخرة. |
| **الإعدادات** | إدارة المستخدمين وصلاحياتهم. |

### الصلاحيات

| الصلاحية | ما يراه |
|---|---|
| **مدير النظام** | كل شيء + إضافة المستخدمين وحذفهم. |
| **مدير مبيعات** | كل سجلات الفريق، ويوزّع المهام، لكنه لا يدير المستخدمين. |
| **موظف مبيعات** | العملاء والصفقات المسنَدة إليه فقط. |

## التشغيل خطوة بخطوة

تحتاج أولًا تثبيت **Node.js** نسخة 20 أو أحدث من [nodejs.org](https://nodejs.org)
(اختر النسخة LTS واضغط Next حتى النهاية).

بعدها افتح موجّه الأوامر داخل مجلد المشروع ونفّذ الأوامر بالترتيب:

```bash
# 1) تثبيت المكوّنات (مرة واحدة فقط)
npm install

# 2) إعداد ملف الإعدادات
cp .env.example .env      # على ويندوز:  copy .env.example .env

# 3) إنشاء قاعدة البيانات وتعبئتها ببيانات تجريبية
npx prisma migrate deploy
npm run db:seed

# 4) بناء النظام وتشغيله
npm run build
npm start
```

ثم افتح المتصفح على: **http://localhost:3000**

### بيانات الدخول الأولى

| الحساب | البريد | كلمة المرور |
|---|---|---|
| مدير النظام | `admin@fasttrans.local` | `ChangeMe123!` |
| مدير مبيعات | `manager@fasttrans.local` | `ChangeMe123!` |
| موظف مبيعات | `agent@fasttrans.local` | `ChangeMe123!` |

> ⚠️ **غيّر كلمات المرور فور أول دخول** من: الإعدادات ← تغيير كلمة المرور.

### تخصيص اسم شركتك

افتح ملف `.env` بأي محرّر نصوص وعدّل:

```
NEXT_PUBLIC_COMPANY_NAME_AR="مكتب فاست ترانس للترجمة"
NEXT_PUBLIC_COMPANY_NAME="Fast Trans Translation Office"
AUTH_SECRET="ضع هنا أي نص عشوائي طويل"
```

ثم أعد التشغيل (`npm run build` ثم `npm start`). الاسم يظهر في الواجهة وفي
عروض الأسعار المطبوعة.

### تفريغ البيانات التجريبية

عند الجاهزية للعمل الحقيقي، احذف ملف `prisma/dev.db` ثم:

```bash
npx prisma migrate deploy
npm run db:seed          # يُنشئ حسابات الدخول فقط لأن القاعدة فارغة
```

## 🚀 النشر على سيرفر (لتراه أنت والفريق من أي مكان)

بعد النشر، أي تعديل يُرفع على `main` **يظهر على الموقع تلقائيًا خلال دقيقتين**
بلا أي خطوة منك.

---

### الطريقة الموصى بها: Vercel

أسهل منصة لهذا النوع من التطبيقات. تحتاج شيئين فقط: قاعدة بيانات + المشروع.

#### الخطوة ١: أنشئ قاعدة البيانات (٣ دقائق، مجانية)

1. افتح [**neon.com**](https://neon.com) ← **Sign up** بحساب **GitHub**
2. سيطلب اسم المشروع — اكتب `crm` واضغط **Create**
3. تظهر لك صفحة فيها صندوق **Connection string** — اضغط زر النسخ 📋 بجانبه

   النص المنسوخ يشبه:
   ```
   postgresql://neondb_owner:XXXX@ep-xxx.eu-central-1.aws.neon.tech/neondb?sslmode=require
   ```
4. **احتفظ به** — ستلصقه بعد قليل

#### الخطوة ٢: انشر المشروع (٥ دقائق)

1. افتح [**vercel.com**](https://vercel.com) ← **Sign up** بحساب **GitHub**
2. من الصفحة الرئيسية اضغط **Add New…** ← **Project**
3. تظهر قائمة مستودعاتك — بجانب `crm` اضغط **Import**
4. تفتح صفحة الإعداد. وسّع القسم المسمّى **Environment Variables**
   وأضِف هذه الثلاثة (اسم في الخانة اليسرى، قيمة في اليمنى، ثم **Add**):

   | Name | Value |
   |---|---|
   | `DATABASE_URL` | الرابط الذي نسخته من Neon |
   | `AUTH_SECRET` | أي نص عشوائي طويل (٣٢ حرفًا فأكثر) |
   | `ADMIN_PASSWORD` | كلمة مرور دخولك (٨ أحرف فأكثر) |

   > اختياري: `NEXT_PUBLIC_COMPANY_NAME_AR` لاسم مكتبك،
   > و`ADMIN_EMAIL` لتغيير بريد الدخول عن الافتراضي.

5. اضغط **Deploy** وانتظر ٣–٥ دقائق

ستحصل على رابط مثل `https://crm-xxxx.vercel.app`. افتحه وسجّل الدخول بـ:

| | |
|---|---|
| البريد | `admin@fasttrans.local` |
| كلمة المرور | التي كتبتها في `ADMIN_PASSWORD` |

**النظام يجهّز جداول القاعدة ويُنشئ حساب المدير بنفسه أثناء النشر** — لا أوامر
ولا خطوات إضافية. وإعادة النشر لاحقًا لا تمسّ بياناتك ولا تُعيد ضبط كلمات المرور.

#### لماذا هذه الطريقة أسهل؟

- **مجانية بالكامل** للاستخدام الداخلي (Vercel و Neon كلاهما مجاني للبداية)
- **لا ينام السيرفر** ولا تُحذف قاعدة البيانات بعد مدة
- **النشر تلقائي**: كل تعديل على `main` يظهر على الموقع خلال دقيقتين
- تحصل على **رابط معاينة منفصل** لكل Pull Request قبل الدمج

### بدائل

| المنصة | الملف الجاهز |
|---|---|
| **Render** | `render.yaml` — قاعدته المجانية تُحذف بعد ٣٠ يومًا وسيرفره ينام |
| **Railway** | `railway.json` + `Dockerfile` — ~٥$ شهريًا، لا ينام |
| **سيرفر خاص** | `Dockerfile` — أي منصة تدعم Docker |

### الإعدادات على أي سيرفر

| المتغيّر | مطلوب؟ | القيمة |
|---|---|---|
| `DATABASE_URL` | ✅ | رابط قاعدة PostgreSQL |
| `AUTH_SECRET` | ✅ | نص عشوائي طويل (مفتاح تشفير الجلسات) |
| `ADMIN_PASSWORD` | ✅ | كلمة مرور أول حساب مدير |
| `ADMIN_EMAIL` | — | الافتراضي `admin@fasttrans.local` |
| `NEXT_PUBLIC_COMPANY_NAME_AR` | — | اسم مكتبك بالعربية |
| `DATABASE_PROVIDER` | — | يُستنتج تلقائيًا من رابط القاعدة |

### الفحص التلقائي عند كل تعديل

ملف `.github/workflows/ci.yml` يجعل جيت هب — عند كل رفع — يبني النظام
ويشغّل الاختبار الكامل (١٦ سيناريو) في متصفح حقيقي مقابل قاعدة PostgreSQL.
فإن كسر أي تعديل شيئًا، تظهر علامة ❌ على المستودع قبل وصوله للسيرفر.

### تنظيم الفروع

| الفرع | دوره |
|---|---|
| `main` | النسخة المعتمدة — **وهي التي تُنشر على السيرفر** |
| `claude/...` | فرع التطوير — يُعمل عليه ثم يُدمج في `main` |

### قاعدة البيانات: محليًا وعلى السيرفر

- **على جهازك:** SQLite — ملف واحد بلا إعداد
- **على السيرفر:** PostgreSQL — يتحمّل عدة موظفين ولا تضيع البيانات

النوع يُستنتج تلقائيًا من `DATABASE_URL`، ونفس الكود يعمل على الاثنين.

## نسخة احتياطية

**على جهازك (SQLite):** كل بياناتك في ملف واحد `prisma/dev.db`. انسخه دوريًا
إلى مكان آمن. لاستعادة نسخة قديمة، أوقف النظام وضع الملف مكان الحالي ثم شغّله.

**على السيرفر (PostgreSQL):** Neon يحتفظ بتاريخ التعديلات ويتيح الرجوع لأي
لحظة سابقة من تبويب **Branches / Restore**. ولأخذ نسخة يدوية على جهازك في أي
وقت، استخدم رابط القاعدة نفسه:

```bash
pg_dump "الرابط_هنا" > backup-2026-08-01.sql
```

وللاستعادة:

```bash
psql "الرابط_هنا" < backup-2026-08-01.sql
```

## ملاحظات تقنية للمطوّرين

مبني على Next.js (App Router) + Prisma + SQLite + Tailwind CSS.

### قرارات تصميم مهمة

أثناء بناء النظام واجهنا سلوكًا غير موثوق في التنقّل والحفظ من جهة المتصفح،
وقِسناه بالتجربة المتكررة، فاتُّخذت هذه القرارات:

1. **كل عمليات الحفظ تمرّ بنماذج HTML تقليدية** (`POST` ثم تحويل) عبر المسارات
   `/api/save` و`/api/mutate` و`/api/notes` و`/api/auth` — بدل Server Actions.
   السبب: رحلة الـ Server Action كانت تتوقّف أحيانًا فيُحفظ السجل على الخادم
   خلال أجزاء من الثانية بينما يبقى الزر معلّقًا على "جارٍ الحفظ..." ولا يرى
   المستخدم النتيجة (فشلت نحو نصف المحاولات في القياس). النماذج التقليدية
   نجحت في كل المحاولات، وتعمل حتى لو تعطّل الجافاسكربت.

2. **الروابط وسوم `<a>` عادية** (`src/components/link.tsx`) بدل مكوّن `Link`.
   السبب: التنقّل من جهة المتصفح كان يتوقّف في نحو ثلث المحاولات. التنقّل
   العادي يفتح الصفحة في كل مرة. الكلفة مقبولة لأن الصفحات تُبنى في أجزاء من
   الثانية، والفائدة أن كل رابط يعمل بشكل مؤكد.

3. **البحث والفلاتر نماذج `GET` عادية** (`src/components/filters.tsx`) للسبب نفسه.

4. **SQLite في وضع WAL** مع `busy_timeout` (انظر `src/lib/db.ts`) ليتحمّل
   القراءة والكتابة معًا عند استخدام عدة موظفين في الوقت نفسه.

### الاختبار

```bash
npx playwright install chromium   # مرة واحدة فقط
npm start                          # في نافذة
npm run test:e2e                   # في نافذة أخرى
```

يفتح متصفحًا حقيقيًا ويمرّ على ١٦ سيناريو: الدخول، إنشاء عميل، تحويله إلى
صفقة، إضافة ملاحظة ومهمة، عرض سعر بحساب تلقائي، الصلاحيات، وعرض الجوال.

### تبديل قاعدة البيانات

لا يحتاج تعديل الكود: ضع رابط PostgreSQL في `DATABASE_URL` وسيتعرّف النظام
عليه تلقائيًا (`scripts/db-provider.mjs`). واتركه فارغًا للعمل بـ SQLite محليًا.
